# Budget Tracker

An offline-first personal budget tracker built with Expo SDK 57 (Expo 57.0.20), React Native 0.86.3, React 19.2.3, Expo Router 57, NativeWind 4, and Zustand.

## Version 1.1.0

The app's display/release version is `1.1.0`, configured by `expo.version` in `app.json`. The npm package version in `package.json` remains `1.0.0` and is not the app's display version.

- Budgets and expenses use Philippine pesos. Categories are Internet, Electricity, Water Bill, Allowance, Grocery, and Other.
- New Budget opens with an empty amount; `0.00` is a placeholder, not a prefilled value. Edit Budget prefills the selected budget's amount. Neither budget nor expense forms auto-focus inputs; tap an input to open the keyboard.
- A new budget starts and ends today, with no date picker. It closes the previous budget on the new budget's start date, never before the previous budget's own start date. The newest-created budget remains active until another is created, even when the phone date changes.
- History contains only past budgets, read-only and grouped newest-first. Expenses belong to their original budget via `sheetId`, not date-range matching.
- Home and History remain the two bottom tabs. The gear in Home's header opens a full Settings screen with a native stack back arrow, even before a budget exists. Settings contains Data (Backup and Restore) and Information (how to use, privacy/local storage, and About).
- Settings shows the installed binary's version using `expo-application`. Expo Go and runtimes without a native version show a labeled Expo config fallback, not the Expo Go host version or npm package version. SDK 57 removed `Constants.nativeAppVersion`, so `expo-application` is needed for accurate native version reporting.
- The non-scrollable budget and expense sheets share `hooks/useKeyboardSheet.ts`. It measures the modal container and sheet, accounts for Android Dialog resizing before applying any remaining keyboard lift, and constrains movement against the top safe area. On screens too short for the whole form, keeping the top reachable does not guarantee every control fits; small-screen and large-text behavior still needs device verification.

## Get started

Use Node.js 22.13 or newer (a supported LTS release is recommended). SDK 57 supports iOS 16.4+ and Android 7+. Native iOS builds require Xcode 26.4+ on macOS or EAS Build; Windows can run Metro and export iOS JavaScript bundles.

1. Install dependencies:

   ```bash
   npm install
   ```

2. Start the Expo development server:

   ```bash
   npm start
   ```

Use the terminal shortcuts or Expo Go to open the app on a device. You can also run:

```bash
npm run android
npm run ios
npm run web
```

The project uses Expo's managed/CNG workflow. Native `android` and `ios` projects are generated by Expo when a native build needs them and are not committed.

For a physical iPhone, confirm that the installed Expo Go supports **SDK 57**, then run `npx expo start --clear` and scan the QR code with the phone on the same network. Expo Go distribution can differ between the App Store and TestFlight; see [Expo Go availability](https://expo.dev/go) if the installed client reports a different SDK. Existing development/standalone builds must be rebuilt after this SDK upgrade.

## Local data and backups

Application data is persisted locally with AsyncStorage 2.2.0 under `budget-tracker-storage`, so core budgeting functionality remains available offline. Persistence remains at version 3, independent of the app release version. Version mismatches no longer reset budgets and expenses.

### Safe startup and recovery

- Startup validates the complete version-3 envelope using the same validator as Restore, before Zustand merges anything. Valid data loads without rewriting the original JSON, including legacy optional boolean `hydrated` values. A missing storage key (`null`) alone starts a new empty budget store; an empty string or malformed payload is an error, not a fresh install.
- No older-version conversion is supported. Reachable Git history introduces the store already at version 3 (`8f12cef`); the preceding commit (`47984a7`) is the Expo starter without budget persistence. There is no documented version-0/1/2 layout to migrate safely. Missing, nonnumeric, or unsupported versions are rejected even if their arrays look current.
- The historical `Expense` type allowed a missing `sheetId`. Such records, dangling references, and other invalid data are preserved in storage but block startup. The app never guesses expense-to-budget relationships from dates, drops invalid records, or replaces rejected input with empty arrays.
- Hydration status is separate from persisted financial data. Action setters, external store setters, and persistence writes are blocked while loading or failed. The persistence clear-storage method does not delete data. After successful hydration, edits are enabled and subsequent writes contain only sheets and expenses, still at version 3.
- Editing screens are not mounted until hydration succeeds. A read still pending after three seconds shows a locked explanation instead of hanging on the logo or unlocking empty defaults. If storage never responds, completely close and reopen the app; retry/restore are disabled while that read is pending to avoid overlapping operations.
- A failed read or validation opens recovery with **Export original JSON**, **Restore compatible backup**, and **Retry reading local data**. Export reads the raw storage without validating or repairing it; an exported older/damaged file is not necessarily restorable. Android confirms only a completed write; iOS share completion does not confirm a saved copy. Restore explicitly confirms replacement, accepts only validated version-3 JSON, and requires a complete close/reopen before editing. Export the original first if it matters.
- This prevents the app's startup fallback from overwriting rejected input, not every possible loss. File-provider/storage access can fail, old data may require manual review, and records already erased by an older app cannot be recovered by this change. Do not uninstall or clear storage to resolve a recovery error.

Run both regression suites with `node --experimental-strip-types --test lib/restoreBackup.test.mjs store/safePersistence.test.mjs`. They exercise the real Zustand persistence middleware with in-memory storage, including successful hydration, rejected formats, raw-byte preservation, setter gating, pending/failed reads, retry, and restore followed by restart. Native recovery-screen and file-provider interactions still need device testing.

### Backup and Restore

Open **Home > Settings (gear) > Data** for **Backup** and **Restore**:

- On Android, Backup asks for a folder through the Storage Access Framework (SAF) and writes the raw stored JSON as UTF-8 using base name `budget-tracker-backup` and MIME type `application/json`.
- On iOS, Backup writes `budget-tracker-backup.json` to cache and opens the share sheet. Choose a destination to keep a copy. Share-sheet completion cannot confirm that a file was actually saved, so this path shows no save-success toast. Android shows one only after the file write succeeds. Canceling a picker or denying folder access produces no success message; missing stored data produces a "Nothing to back up yet" notice.
- Restore picks a JSON document with `copyToCacheDirectory: true` and reads its URI using `fetch`. Before overwriting local storage, it requires persistence version 3 and validates the state arrays, record fields, positive finite amounts, calendar dates, timestamps, known categories, unique IDs per collection, and expense-to-budget references. Invalid or unsupported backups are rejected without writing. Compatible raw JSON is preserved rather than merged or migrated.
- Restore first asks for confirmation before opening the picker. **Close the app completely and reopen it immediately after a successful restore.** The running Zustand store is not rehydrated automatically. Settings keeps a restart notice visible and blocks return to editing until restart; making further changes could overwrite the restored data with the old in-memory state.
- Local file reads through `fetch` can fail depending on runtime/provider behavior. Restore failures are reported separately from success, with wording covering file access, validation, and storage failures. Validation checks structure and relationships, not the authenticity or accuracy of financial records. Run the focused regression tests with `node --experimental-strip-types --test lib/restoreBackup.test.mjs` (no additional test dependency).
- Data actions share an immediate operation lock, released in `finally` on success, failure, or cancellation (including dismissal of the confirmation). Navigation away is blocked while an operation is pending. A canceled or failed attempt leaves the actions available for retry.

AsyncStorage is not an encrypted vault. Exported JSON backups and PDFs are unencrypted and contain sensitive financial information; keep them in trusted locations. The app does not automatically sync records to the cloud, but a file provider or sharing destination chosen by the user may store copies there.

Expo Go and standalone APKs have separate private storage. **Expo Go cannot read or recover data from an old installed APK.** Moving data requires a usable backup exported from the app/container that holds it. If the old APK cannot export, launching the latest code in Expo Go does not solve that limitation. Do not uninstall the data-holding app or clear its storage if you need to retain its records.

## PDF export

In History, tap a past budget's document icon and confirm export to generate its budget summary and expense table. `lib/generatePdf.ts` uses `pdf-lib` with standard Helvetica fonts, not a native print service. PDF amounts use the `PHP ` prefix instead of the peso symbol for font compatibility; arbitrary Unicode expense titles are not guaranteed to render.

- Android asks for a destination folder using SAF and writes the PDF there. The requested name is `MM-DD-YY.pdf`, based on the budget's **start date**, not the export date. The file provider controls the final name and duplicate handling. After the write succeeds, History shows a success toast containing the requested filename. Canceling or denying folder access produces no save-success toast.
- iOS opens the share sheet for a cached `budget-record.pdf`; use Save to Files or another destination. This path does not show the Android save-success toast and cannot confirm that the user saved a copy.

PDFs are reports, not restorable backups. Use JSON Backup for data transfer.

## Builds and upgrades

`eas.json` uses `appVersionSource: "remote"`. Preview and production have `autoIncrement: true`, which increments Android `versionCode` or iOS `buildNumber`, **not** the display version in `app.json`. Development has no auto-increment configured. Update `expo.version` explicitly for a new display/release version.

An Android in-place upgrade requires the same package (`com.budgettracker`) and signing certificate, with an appropriate higher `versionCode`. Preserve the EAS signing credentials and install the update over the existing app rather than uninstalling it. This enables an upgrade but is not a data-retention guarantee: clearing storage, uninstalling, or triggering the reset migration can lose data. Keep a usable backup where possible.

A standalone APK contains the code baked into its build. These changes require rebuilding and installing the new APK; they do not appear in an already installed APK simply by restarting Metro. Expo Go loads current development code but still uses its own storage container.

Dependency alignment uses Reanimated 4.5.1 with Worklets 0.10.1 and preserves the NativeWind/Tailwind 3 Babel and Metro configuration. Refer to the [SDK 57 docs](https://docs.expo.dev/versions/v57.0.0/) and [official upgrade walkthrough](https://docs.expo.dev/workflow/upgrading-expo-sdk-walkthrough/) for future updates.
